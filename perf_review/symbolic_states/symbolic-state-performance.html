Symbolic State Performance

What limits linear algebra with symbolic states in large Hilbert spaces, what FermionicHilbertSpaces (FHS) can fix itself, and what it needs from NonCommutativeProducts (NCP).

Summary

Four new tutorials use symbolic kets as sparse vectors in spaces of dimension 264 to 2200: an η-pairing tower, a Hubbard bound state found with KrylovKit eigsolve, a Schrieffer–Wolff Kondo coupling found with linsolve, and the fourth-order toric-code coupling of the Kitaev honeycomb model. All four reproduce their analytic results. The problem sizes they can reach, however, are set by overhead rather than by the physics:

  • Inner products of two ket sums form every pair of terms. At 1024 terms, inner takes 624 ms. A dictionary lookup takes 0.02 ms.
  • Operator times ket sum goes through generic symbolic sorting. Zero products are removed one at a time from the middle of a vector, so the cost per pair grows with the problem size. Applying each operator term directly to the basis states is 25–75× faster.
  • Abstract key types: ket sums are keyed by NCMul{Int,AbstractSym,Vector{AbstractSym}}, so hashing and comparison go through dynamic dispatch.
  • BigInt Fock states are used from 64 modes upward. Applying an operator to a basis state then costs 10–40× more than with UInt64.

Recommendation. FHS should add a concrete sparse state type, keyed by basis state, with a direct operator-application kernel and fixed-width Fock integers. This removes the hot path from NCP and fixes most of the ergonomic problems as well.

Independently, NCP should make products of sums linear in the number of term pairs and offer a few extension points. Those changes benefit symbolic operator algebra in general, including commutators, powers of H and operator growth, which a state type does not cover.

Measurements

The measurements use a spinful Hubbard ring with L sites (2L modes), a two-particle ket sum with L2 terms, and a Hamiltonian with 5L terms. They were taken with Julia 1.13, NCP 0.5.0 and FHS main, using one thread and the minimum of warm runs. The "direct" column applies each operator term to each basis state with the same kernel that matrix_representation uses, and accumulates the result in a Dict. It is a 15-line prototype, and its results agree term by term with ham * ψ.

The current paths scale badly:

  • Inner product: four times as many terms makes inner 43 times slower, roughly n2.7.
  • Operator application: the cost per pair of ham * ψ rises from 0.6 µs to 2.3 µs as the problem grows.

The tutorials ran into the same limits:

  • η-pairing: ham * ψ on 4950 terms with 500 Hamiltonian terms took 114 s. Applying the Hamiltonian term by term took 4 s.
  • Bound state: Lanczos stalls beyond L = 24 because of norm, so the page uses L = 16.
  • Kitaev: the page computes diagonal energies as inner(t, H0*t). On 4851 terms this took 134 s and allocated 75 GB, so the page applies the middle resolvent only to the shared terms.

Where the time goes

1. Inner product forms all pairs

VectorInterface.inner(x, y) (NCP src/vectorinterface.jl) evaluates x' * y with autosort on and then reads off the scalar. For kets, x' is a sum of n bras, and the product is a vector of n·m two-factor products. Each one is sorted with mul_effect(bra, ket), which returns 0 or 1. Almost all pairs vanish. Every zero is removed with deleteat! from the middle of the vector of products (_apply_effect!! in src/sorting.jl), and that is where the extra exponent comes from. Profiling in the η-pairing run attributed 86% of the time to unsafe_copyto! under deleteat!.

2. Operator × ket sum uses generic sorting

ham * ψ goes to _add_sorted_products!! (NCP src/add.jl). It collects all m·n products such as [c†, c, ket] into one vector and bubble-sorts them, with the same zero deletion as above. Each mul_effect(op, ket) in FHS (src/symbolic_states.jl:221) then applies one operator factor at a time through _apply_symbolic_operator_to_state, building a one-factor NCMul and its precomputation on every call. The kernel FHS already has for matrices, precomputation_before_operator_application plus _apply_local_operators, applies a whole operator string in one pass, with one precomputation per operator term.

3. Abstract keys

@nc SymbolicState AbstractSym makes every product of an operator and a ket a Vector{AbstractSym} product. After sorting, the single remaining ket factor keeps that container type, and to_add_dict_type keys the sum by NCMul{Int,AbstractSym,Vector{AbstractSym}}. Every hash, every == and every factor access is then a dynamic dispatch. Ket sums also do not keep a stable type through op * x, which KrylovKit's typed containers rely on.

4. BigInt from 64 modes

default_fock_representation (src/physics/fermions/fock.jl:15) picks UInt64 for fewer than 64 modes and BigInt otherwise. Every bit operation on a BigInt allocates. A spinful chain with 32 sites already crosses this threshold.

FHS: proposed fixes

F1. A concrete sparse state type largest gain

The proposal is a vector type for states that is keyed by the basis state of its space and applies operators with the matrix kernel. It sits next to SymbolicState and does not replace it. Symbolic kets, bras and ketbras stay as they are for algebra: ketbras as operators, interleaving across spaces, and representation. The new type is what you use once you want to do linear algebra.

struct SparseState{B,T,H<:AbstractHilbertSpace}
    space::H
    amplitudes::Dict{B,T}       # basis state => amplitude, zeros never stored
end
SparseState(space, amplitudes::Dict{B,T}) where {B,T} = SparseState{B,T,typeof(space)}(space, amplitudes)

# Construction
SparseState(H, label, ::Type{T}=Float64) where {T} = SparseState(H, Dict(interpret_state(label, H) => one(T)))
vacuum(H, ::Type{T}=Float64) where {T} = SparseState(H, Dict(vacuum_state(H) => one(T)))
SparseState(x)                  # from a SymbolicState, or an NCMul/NCAdd of kets in one space, via terms(x)

# Operator application: one precomputation per operator term, then one kernel call per basis state
function Base.:*(op::Union{AbstractSym,NCMul,NCAdd}, ψ::SparseState{B,T}) where {B,T}
    S = promote_type(T, mat_eltype(op))
    out = Dict{B,S}()
    c = additive_coeff(op)                           # the identity part of op
    iszero(c) || foreach(((s, a),) -> out[s] = c * a, ψ.amplitudes)
    for term in operator_terms(op)                   # the non-scalar terms
        precomp = precomputation_before_operator_application(term, ψ.space)
        for (s, a) in ψ.amplitudes
            newstate, amp = _apply_local_operators(term, s, ψ.space, precomp)
            iszero(amp) && continue
            out[newstate] = get(out, newstate, zero(S)) + amp * a
        end
    end
    filter!(kv -> !iszero(last(kv)), out)
    return SparseState(ψ.space, out)
end

# Inner product: iterate the smaller dictionary, look up in the larger
function VectorInterface.inner(ψ::SparseState, φ::SparseState)
    _check_same_space(ψ, φ)
    a, b, flip = length(ψ) <= length(φ) ? (ψ, φ, false) : (φ, ψ, true)
    S = promote_type(scalartype(ψ), scalartype(φ))
    z = sum((conj(v) * get(b.amplitudes, s, zero(S)) for (s, v) in a.amplitudes); init=zero(S))
    return flip ? conj(z) : z
end

Design decisions to make:

  • Constrained spaces. Checking whether each new state is in a ConstrainedSpace may require its basis. The simplest rule is that a SparseState lives in an unconstrained space, and symmetries are respected because the operators conserve them.
  • Amplitude type closure. op * ψ promotes the amplitude type, for example to complex for Sy. KrylovKit requires apply to return the type of its input vector. Starting from a complex vector covers this, and the docs should say so.
  • Repeated application. In Krylov loops, the precomputations could be cached in a prepared operator. Their cost is proportional to the number of operator terms, which is small next to (operator terms) × (state terms), so this can wait.
  • Naming. SparseState is a placeholder. It could instead be what Kets(H) returns in a later release, if the duplication proves confusing.

Tests:

  • Compare op * ψ with the existing symbolic path and with matrix_representation(op, H) * vector_representation(ψ, H), over random small operators on fermionic, spin, boson, product and Majorana spaces.
  • Check VectorInterface conformance with VectorInterface.TestUtils, if available.
  • Add a KrylovKit eigsolve smoke test.

Effort: roughly 250 lines plus tests.

F2. Fixed-width Fock integers above 63 modes

Change default_fock_representation (src/physics/fermions/fock.jl:15–20) to use UInt64 up to 63 modes, UInt128 up to 127, and a fixed-width type above that. There are two options for the fixed-width type:

  • BitIntegers.jl, which adds a dependency and provides UInt256, UInt512 and so on.
  • A small NTuple{K,UInt64} bitstring type implementing &, |, ⊻, ~, shifts, count_ones, iszero, hash and isless. The fermion kernel uses only these operations, plus parity counts of masked bits.

Keep BigInt only as an explicit opt-in.

Also review the indexing side:

  • dim (fermions.jl:39) still needs BigInt for the count.
  • state_index computes state.f + 1. That cannot overflow below the width limit, but symbolic-only workflows never need it.

The measured gap per kernel call is 8 ns with UInt64 against 90–340 ns with BigInt. UInt128 should be close to UInt64; I have not measured it.

Effect on the tutorials

With F1 to F3, each page gets shorter and can reach larger sizes:

  • η-pairing: the term-by-term workaround goes away, and n = 3 at L = 100 (161 700 terms) becomes feasible.
  • Bound state: L of 100 or more becomes feasible. Lanczos cost then scales with L2 per iteration.
  • Kitaev: the internal .dict access and the dictionary-lookup workaround both disappear.
  • Kondo: loses import inner and the padded vacuum string.

Suggested order

  1. F3 items that need no new type: vacuum, tuple labels, dot in the docs, and show. These are small PRs that can land right away.
  2. F2, fixed-width integers. This change is self-contained and also speeds up matrix building for spaces with 64 or more modes.
  3. F1, SparseState, in its own PR with tests. Then rewrite the four tutorials on top of it.

NCP: requirements

The requirements below come from FHS's use of NCP as the arithmetic for basis kets and operators. Each one states what we need and why, and gives a loose idea for meeting it. The NCP developers know the internals better, and a different solution is welcome as long as it meets the requirement.

N1. Products of sums cost a constant amount per term pair

Requirement. For a * b with m and n terms, the time should be proportional to m·n (times the sorting work per product). Peak memory should be bounded by the size of the result plus a small working set, not by m·n. Products that sort to zero should cost no more than sorting them.

Why. H * ψ and x' * y produce mostly zero products. Removing them one at a time with deleteat! from a vector of all products (_apply_effect!!, reached from _add_sorted_products!!) makes the cost per pair grow with the problem size. Measured: 0.6 µs to 2.3 µs per pair from 20k to 164k pairs, and 114 s against 4 s for the same work split term by term.

Acceptance. The time per pair of ham * ψ stays flat across about 104 to 106 pairs.

Loose idea. Sort each product to completion and add it straight into the result dictionary, instead of keeping all products in one vector. Alternatively, mark zeros and compact once, or swap-remove instead of deleteat!.

N2. Inner products that do not form every pair

Requirement. When the terms of x and y contract pairwise to scalars, and downstream can say which pairs can be nonzero, inner(x, y) should cost about O(nx + ny). In FHS's case, the nonzero pairs are those with equal basis states. The result must still match scalar(x' * y).

Why. Krylov methods call inner and norm several times per iteration. With all pairs formed, they dominate the run: one norm takes 1.1 s at 1024 terms, against 0.4 s for applying H.

Loose idea. Add an opt-in hook. An atom type declares a hashable contraction_key(term), or a contract_terms(a, b) together with a key, so that NCP can group the terms of y by key and pair only terms with matching keys. Another option is a public function that inner calls, which downstream can specialize on the key type. N1 alone would already bring this down from about n2.7 to n2.

N3. Concrete, stable term types

Requirement. When every factor of a sorted result has the same concrete type, the sum's key type should use that type rather than the declared supertype of the mixed product. Downstream should also be able to rely on op * x returning typeof(x) when x is a sum of kets and op maps kets to kets.

Why. Keys of type NCMul{Int,AbstractSym,Vector{AbstractSym}} make every hash and comparison dynamic. KrylovKit stores vectors in containers typed by the first vector, so type changes between iterations either error or force conversions.

Loose idea. Narrow the factor container to the element type it actually holds when building the result in _sum_sorted_terms. Alternatively, add a hook through which downstream declares the result key type for a pair of operand key types.

N4. An extension point for multiplying two terms

Requirement. Downstream should be able to supply the result of term × term for given factor types, bypassing mul_effect between adjacent factors. It should also be able to do per-left-term preparation once and reuse it for every right term.

Why. FHS can apply a whole operator string to a basis state in one kernel call, with a precomputation per operator term. That is about 8 ns per pair, against about 600 ns through pairwise mul_effect. Today that kernel is only reachable outside NCP arithmetic.

Loose idea. Add mul_terms(a::NCMul, b::NCMul), which defaults to catenating and sorting and which downstream specializes on factor types. A prepare(a) and mul_terms(prepared, b) pair would cover the reuse. If F1 lands in FHS, this matters less for states, but it would still speed up mixed expressions.

N5. Cheap public access to terms

Requirement. NCP should provide public ways to:

  • count the terms of a sum in O(1);
  • iterate over (key or factors, coefficient) pairs without allocating an NCMul per term;
  • map a function of (term, coefficient) over a sum to produce a new sum.

Why. The tutorials reached into x.dict to count terms and to apply a diagonal resolvent. terms(x) is a filtered iterator with no length, and NCterms allocates a product per term.

Loose idea. Add nterms(x), pairs-style iteration over the internal dictionary as a public read-only view, and map_coefficients(f, x) where f receives the term too.

N6. Fewer allocations per product

Requirement. Forming and sorting a short product, with up to about four factors, should allocate at most once.

Why. catenate uses vcat, and the Kondo run showed about 667k allocations for one application of an 83-term operator to a 100-term state.

Loose idea. Use tuple-backed products through sorting where the length is known, or reuse scratch buffers for catenation.

Priority from FHS's side: N1 first, because it helps every user of NCP and needs no new API. Then N3 and N5. N2 and N4 matter less once FHS has its own state type, but they remain the general solution for mixed symbolic expressions.

How this was measured

The measurements come from bench.jl (current paths) and direct.jl (prototype kernel) on an i7-13700T running Windows 11, with --threads=1. The η-pairing, Kondo, bound-state and Kitaev figures were reported by the agents that wrote those tutorials, which are on the branch symbolic-showcases. The NCP source references are to version 0.5.0 (commit 85bf84c).
